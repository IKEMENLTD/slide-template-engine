## Phase 0 の前提（着手前に返すことになっていた3点）

要件定義書 0章の手順では、全文を読んだあと、下の3点を返して承認を待つことになっている。2026-10-26 に佐藤さんから「進めて」と指示があったので、承認を待たずに Phase 0 を実施した。3点はここに残す。

### 理解した要点

1. 原稿 → 設計図（deck-plan.json）→ .pptx／PDF を作る CLI を作る。AI の出力は設計図で止まり、その先はコードだけで進む。
2. デザインの正本はデザイナーが作る PowerPoint テンプレート。見本スライドを複製し、名前の付いた図形（txt./num./img.）の中身だけを差し替える。
3. AI が決めるのは、型・欄ごとの文言・強調する語だけ。色・位置・大きさ・フォントは決めさせない。
4. 字は小さくしない。入らなければ削るか、別の型を使う。原稿に無い数字・固有名詞は検査で止める。
5. 字数の上限・型の情報はカタログに1か所だけ置き、プロンプトと検査の両方がそこから読む。
6. Phase 0 では、pptx-automizer・LibreOffice での描画・gpt-image-2.5-flare・fontkit の4点を実物で確かめる。

### Phase 0 の作業計画（実施済み）

1. 検証用の小さいテンプレート（名前付き図形・平行四辺形の写真枠・テーマ色）をスクリプトで作る
2. pptx-automizer で複製・差し替えを行い、出力の構造を機械で検査する
3. LibreOffice（Docker）で PDF と PNG にして見た目を確かめる
4. gpt-image-2.5-flare で、生成 → 見本1枚の編集 → 見本2枚の編集 を行う
5. fontkit の予測と LibreOffice の折り返しを 36 通りで突き合わせる
6. PowerPoint で開く確認は人（佐藤さん）が行う → `out/phase0/README.md`

- **それでも守ること**：有償フォント（DIN Next LT Pro・リュウミン・太ゴB101）と API キーはリポジトリに入れない。`fonts/` には OFL のフォントだけを置く（`OFL-*.txt` 同梱）。

## D-002 スライドの大きさは PowerPoint 標準のワイド（13.333 × 7.5 in）

- 先方 PDF は 1920 × 1080 pt。PowerPoint の標準ワイド（960 × 540 pt）にちょうど 0.5 倍で写る。
- 1920 pt の幅のまま作ると、PowerPoint の既定の文字の大きさや画面表示と合わず、先方が直すときに扱いにくい。
- 仮テンプレートの座標は「PDF の pt × 0.5」で書く。

## D-003 写真の切り抜きは sharp で先に行う

- **何を**：枠の縦横比に合わせた切り抜きとモノクロ化を sharp で済ませてから、automizer の `setRelationTarget` で画像だけ差し替える。
- **なぜ**：automizer 0.9.4 の `setRelationTargetCover`（縦横比に合わせて切り抜く機能）は、平行四辺形の写真で `Skipped setting relation target cropped due to an error: Cannot read properties of undefined (reading 'getAttribute')` を出して切り抜きを飛ばした（画像は差し替わるが引き伸ばされる）。要件 7章 C にもともと「sharp で切り抜く」とあるので、その通りにする。
- **分かったこと**：中央で切り抜くと、人物の顔が平行四辺形の斜めの辺で切れることがある（`render/probe-out-01.png`）。Phase 3 で、写真ごとの「切り抜きの中心」（`photos.json` で指定、無ければ sharp の `attention`）を入れる。

## D-004 automizer の出力は「掃除」と「構造検査」を必ず通す

- **何を**：`src/assemble/sanitize.ts`（掃除）と `src/check/pptx-structure.ts`（PPTX_REPAIR の構造検査）を作った。
- **なぜ**：automizer の出力をそのまま調べると、構造の問題が **8件** あった（`evidence.json` の `raw.issues`）。
  - `removeExistingSlides` で外した見本スライドとそのノートが、部品として残る。`cleanup: false` だと、スライドとノートが互いに参照し合う輪になって残る。「どこからも参照されていない」という数え方では見つからず、**ルートからたどれるか**で数える必要があった
  - 写真を差し替えると、元の画像への関係が残る。`cleanup: true` では画像だけが消え、関係が宙に浮く（PowerPoint が「修復」を出す典型）
  - 見本スライドのノート（型の YAML）が成果物に写る
- **掃除の中身**：スライドからノートへの関係を外す／本文で使われていない画像の関係を外す／ルートからたどれない部品を、変化が無くなるまで消す。足すことはしない。掃除後は **0件**。
- **テスト**：正しいものは通る・壊したものは落ちる、の両側（`test/pptx-structure.test.ts`）。検査と掃除をわざと壊すと、テストが落ちることも確かめた。
- **捨てたもの**：automizer の `cleanup` に任せること。
- **残る不確かさ**：この検査は「PowerPoint が修復を出す原因の典型」を数えるだけで、通っても PowerPoint で開ける保証にはならない。最終確認は人が PowerPoint で行う。

## D-005 フォントは静的フォント（.otf）を使い、太さごとに名前で指定する

- **何を**：`fonts/` に Noto Sans JP（Regular・Medium・Bold）、Noto Serif JP（Regular・Medium）、Barlow（Regular・Medium）の**静的フォント**を置く。可変フォントは置かない。
- **なぜ**：
  - Windows に標準で入っている `NotoSansJP-VF.ttf` は可変フォントで、既定の太さが **Thin**。Windows の LibreOffice で描くと、PDF に `NotoSansJP-Thin` が埋め込まれた（細い字で描かれる）
  - PowerPoint の文字の書式は「太字かどうか」しか持たない。Medium は別の名前で指定する必要がある。静的フォントの Medium は名前表の旧来の家族名が **`Noto Sans JP Medium`** なので、テンプレートではこの名前で指定する（fontkit で名前表を読んで確認）
  - DIN の代わりの Barlow は Windows に入っていない
- **描画**：Docker のイメージには、OS の日本語フォントを入れず、`fonts/` だけを入れた。テンプレートが指定したフォントが無いと DejaVu で描かれるので、すぐに気づける。
- **未確認**：PowerPoint が `Noto Sans JP Medium` という名前で Medium を選ぶか（人が確認する）。.otf は PowerPoint にフォントとして埋め込めない（要件の付録A）ので、先方の PC にフォントを入れてもらう必要がある。

## D-006 文字幅の予測の規則と、3% の余裕

- **規則**（`src/fit/measure.ts`）：和文は文字の間ならどこでも折り返せる／行頭禁則（句読点・閉じ括弧・小書きの仮名・長音）／行末禁則（開き括弧）／英数字の連続は途中で折り返さない／和文と英数字の境目の空き（autospace）／句読点のぶら下げ。
- **突き合わせ**（4 字体 × 3 サイズ × 3 幅＝36 件、LibreOffice 7.4）：

| 設定 | 行数が一致 | 改行位置まで一致 | 実物のほうが行が多い（あふれを見逃す） |
|---|---|---|---|
| 何もしない | 32/36 | 15/36 | 1 |
| autospace 0.25em・ぶら下げあり | 34/36 | 27/36 | 2 |
| 上＋LibreOffice の丸めを再現 | 35/36 | 32/36 | 0 |
| **autospace 0.25em・ぶら下げあり・幅の 3% を余裕** | 31/36 | 10/36 | **0** |

- **分かったこと**：
  - LibreOffice は 1 文字の幅を 1/100mm に丸めて足す（20pt の全角は 20.01pt）。そのため、枠の幅がちょうど 20pt の倍数だと 1 文字少なく折り返す
  - 和文と英数字の間に、およそ 0.25em の空きが自動で入る（PDF の文字の位置で実測）
  - 句読点は枠の外にぶら下げる
  - 読点を含む行が、計算より 1 文字多く入る場合が 4 件残った（原因は特定できていない。どれも予測のほうが行が多い、安全な側のずれ）
- **決めたこと**：B段・検査（OVERFLOW）での判定は「autospace 0.25em・ぶら下げあり・幅の 3% を余裕」にする。改行位置までは合わせない（PowerPoint と LibreOffice で違うので、片方に合わせる意味が薄い）。目的は「予測では入るのに、実物ではあふれる」を 0 にすること。値は設定ファイルに置く。
- **捨てたもの**：LibreOffice の丸めを本番の判定で再現すること（描画側の都合に寄せすぎる。検証の再現用にだけ残した）。
- **PowerPoint での突き合わせ（2026-10-26）**：佐藤さんに PowerPoint for the web で `wrap.pptx` を PDF に書き出してもらった（`out/phase0/wrap/powerpoint.pdf`。14ページ・960×540pt）。
  - **ブラウザ版は Noto を持たず、和文を MS ゴシック・英数字を Calibri に置き換えて描いた**（PDF の埋め込み字体で確認）。そのため Noto の文字幅は確かめられない。代わりに、置き換わった字体の幅で予測し直し、**PowerPoint の折り返しの規則**を確かめた（`scripts/phase0/measure-wrap-substituted.ts`。MS ゴシックと Calibri は Windows 同梱の有償フォントなのでリポジトリに入れない）。
  - **PowerPoint は和文と英数字の間に空きを入れない**（実測 ±0.03em）。LibreOffice（0.25em）と違う。
  - 句読点はぶら下げる（LibreOffice と同じ）。
  - 太字の字体が無いとき（MS ゴシック）は、PowerPoint が太字を合成し、1文字の幅が約 0.75% 広がる（20pt で 20.15pt）。

| 設定（PowerPoint・置き換わった字体の幅で予測） | 行数が一致 | 改行位置まで一致 | 見逃し |
|---|---|---|---|
| 空きなし・ぶら下げあり | **36/36** | 31/36 | 0 |
| 空き 0.25em・ぶら下げあり・3% の余裕（本番の判定） | 28/36 | 6/36 | **0** |

- **結論**：本番の判定（空き 0.25em・ぶら下げ・3% の余裕）は、LibreOffice でも PowerPoint でも「あふれの見逃し 0 件」。PowerPoint より空きを多めに見積もるぶん安全側に倒れる。改行位置を PowerPoint に合わせたいときは、空きを 0 にした設定を使えばよい（値は設定ファイルに置く）。
- **まだ確かめられていないこと**：Noto が入った PowerPoint（デスクトップ版）での文字幅。規則は確かめたので、残るのは字体の幅の差だけ。3% の余裕でまかなえる見込みだが、PowerPoint のデスクトップ版が使えるようになったら同じ道具で測り直す。

## D-008 先方資料の読み直し（要件定義書 4章の訂正）

- **大見出しは明朝**：PDF の大見出しはリュウミン（明朝）で、ルール文書と一致している。16章 #3 の既定値「明朝を使わない」は、資料に合わせて **`headline.mincho: true`（代わりの字体は Noto Serif JP）** にするのがよい。Phase 1 の設定の雛形はこの値で作る。先方に確認したいのは「リュウミンの代わりに Noto Serif JP でよいか」の 1 点になる。
- **ゴシックは太ゴB101も使っている**：小見出し・説明文の一部が太ゴB101（モリサワ・有償）。代わりは Noto Sans JP Bold にする。
- **4ページ目は型ではない**：説明のページ。16章 #7 は「型として扱わない」で確定。
- **8ページ目は表紙の別案**：役割は `cover`。

## D-009 強調は「太字＋アクセント色の下線」

- **何を**：強調語は、見本の書式に太字と accent2 色の太い下線を足す。設定は `emphasis: { underline: "accent2", bold: true }` の形にする（6-3 の `color: accent2` から変える）。
- **なぜ**：黄の文字色は白地で読めない。ルール文書 4-4 が挙げる強調の形（黄の下線・黄の図形の中の文字）に合わせる。
- **残ること**：「黄色の図形の中の文字」で強調する型は、図形をテンプレートの飾りとして作り込む（エンジンは図形を足さない）。

## D-010 「グリッドの幅を広げる」は型の選び直しで行う

- ルール文書 8-4 の「必要であれば使用するグリッドの幅を広げる」は、エンジンが枠を広げることではなく、**欄の広い型を選び直す**ことで行う。要件定義書の原則4（枠を広げない）と両立する。
- そのため、件数違いと同じく、文字の多い欄には「幅の広い変種」をテンプレートに用意してもらう必要がある（Phase 5 の手順書に書く）。

## D-011 描画は Docker（標準入出力で受け渡す）

- `docker/render/Dockerfile`：debian bookworm-slim・LibreOffice 7.4.7・poppler-utils・`fonts/`。
- 検証機の docker コマンドは Windows 側のもので、WSL のパスを bind できないため、PPTX を標準入力で渡し PDF を標準出力で受け取る（`scripts/phase0/render.py`）。
- Phase 0 では PNG 化に PyMuPDF を使った（検証機に pdftoppm が無いため）。Phase 4 では Docker の中の pdftoppm を使う。
- Windows の LibreOffice（soffice.exe）でも描けたが、WSL との連携が途中で止まる（`UtilAcceptVsock: accept4 failed`）ことがあり、フォントも可変フォントを拾うので使わない。

## D-012 仮テンプレートの作り方

- `scripts/build-provisional-template.py` が `templates/provisional.pptx` を作る。座標は先方 PDF から機械で抜き出した値の半分（D-002）。図形は多角形（custGeom）で写し、色はすべてテーマ色の参照。
- 型は5つ：`cover`／`issues/2`・`issues/3`・`issues/4`／`numbers/3`。
- 課題3件は、2列だと右下が欠けて見えるので、1列に縦に3つ並べた（PDF には3件の見本が無いので当方の判断）。
- 写真は Phase 0 で生成した写真をモノクロにしたもの（`templates/provisional-assets/`）。先方 PDF の写真は使わない。
- 先方 PDF の左上のロゴは入れていない（会社ごとに違う固定の飾りなので、本番のテンプレートでデザイナーが置く）。
- 表紙の要点の箱の「2,000」だけを大きくする組み方（PDF は 33pt と 15pt の混在）は、1つの欄で表せないので、同じ大きさにした。

## D-013 行間は固定値（pt）で持つ

- テンプレートの欄の行間は「固定値（pt）」にする。倍率指定だと1行の高さが字体の作りで変わり、何行入るかを決められないため。
- 倍率指定・指定なしの欄も読めるが、その場合は「字の大きさ×1.2」で推定し、カタログに「推定」と印を付けて注意を出す。
- 先方デザイナー向けの手順書（Phase 5）に「行間は固定値で」と書く。

## D-014 写真に重ねる色（乗算）は透明度で近づける

- 先方 PDF p3 は、写真の上の青い三角を乗算で重ねている。PowerPoint の図形には乗算が無いので、仮テンプレートでは透明度 88% の図形にした。
- 写真全体に色を重ねる枠（設定 `images.<枠>.multiply`）は、Phase 3 で sharp で乗算してから差し込む（要件 7章 C のとおり）。

## D-015 Illustrator と PowerPoint の字幅の違い（重要）

- **先方 PDF は Illustrator で、カナを詰める設定（プロポーショナル：palt）で組まれている。** PDF の実際の幅は、詰めた幅とほぼ一致した。

| 文言 | 大きさ | 詰めない（PowerPoint） | 詰める（palt） | PDF の実幅 |
|---|---|---|---|---|
| フルスクラッチ | 20pt | 140.0pt | 122.6pt | 127pt |
| 業務が属人化しており、自分がいないと回らない | 13pt | 284.7pt | 266.9pt | 258pt |
| 見積もりを取ったら数百万～数千万と言われた | 13pt | 272.4pt | 261.4pt | 262.5pt |

- **PowerPoint はこの詰めを行わないので、同じ文言でも 5〜14% 幅が広くなる。** 先方デザイナーが Illustrator の感覚で文字量を決めると、PowerPoint では入らなくなる。
- 仮テンプレートでは、字の大きさをできるだけ PDF のまま保ち、余白のあるところは枠を広げた。入らないところだけ字を小さくした：表紙の要点 20→17pt、副題 16→15pt、課題の説明 13→12pt（線も合わせて延ばした）。
- **手順書（Phase 5）に必ず書く**：「PowerPoint で文字を入れて確かめながら枠を決める」「Illustrator の字幅で決めない」。
- 字の大きさを下げたのはテンプレートの作りの段階で、エンジンは字を小さくしない（原則4）のは変わらない。

## D-016 DIN の代わりは Barlow のまま

- Barlow は DIN Next より「2,000」が 23% 広い（「2/3」は 5%、「70」は 1%）。字幅の狭い版（Barlow Semi Condensed）は「2,000」が 9% 広く「70」が 10% 狭いなど、数字によって外れ方が変わる。
- 広いほうに外れるぶん、あふれの判定では安全側なので、要件どおり Barlow のままにする。数字の列は、PDF と同じく真ん中を広く取った。
- 太字の英数字のために Barlow Bold（OFL）を足した。太字の実フォントが無いまま測ると、PowerPoint が太字を合成して広がる分（D-006）を見逃すので、カタログで「注意」を出す。

## D-017 型カタログの作り（`slidegen catalog`）

- `npx tsx src/cli.ts catalog --template templates/provisional.pptx` で、`out/catalog/provisional.catalog.json` を作る。設定ファイルが無ければ雛形を作る（字体は `fonts/` の名前表と突き合わせる）。
- 欄ごとに：枠の位置と大きさ、字の大きさ・太さ・字体・実フォントのファイル、字間、行の高さ、最大行数、1行の字数、最大字数（全角で数える）、英数字だけのときの字数、見本の文言。写真の欄は縦横比と加工。
- 字数は「余裕 3% を引いた幅 ÷ 1字の幅（全角は『国』、数字の欄は『0』）」で数える。AI への目安で、最終の判定は `src/fit/fit-slot.ts` が実フォントで測る（同じカタログの値を読む。原則7）。
- 大見出し（`txt.headline`）の行数は、設定 `headline.maxLines`（2行）を超えない。
- 止める条件：ノートに型の情報が無い／型が重複／欄の名前が重複／自動縮小（文字を縮める）が有効／字体の実フォントが設定に無い／上書きがどの欄にも当たらない／**見本の文言が自分の欄に収まらない**（自己点検）。
- 生成物なので `out/catalog/` に置き、版管理しない（Phase 1 の確認用の写しだけ `out/phase1/` に置いた）。

# Phase 2：原稿から PPTX まで

## D-018 型の追加を Phase 5 から前に出した

- **何を**：Phase 5 の作業「残りの型を仮テンプレートに追加」を Phase 2 の最初に行った。先方 PDF の p5〜p11 から、注意・強調（`attention`）／中扉（`section`）／画像が並ぶ（`steps/3`・`steps/4`）／写真コラージュ（`collage`）／目次（`toc/3`・`toc/4`・`toc/5`）／写真＋本文A・B（`photo-text/a`・`photo-text/b`）の10枚を足し、型は 15・欄は 111 になった。
- **なぜ**：型が表紙・課題・数値の3役割だけだと、10〜20枚の原稿を通すと課題と数値のページが交互に並ぶだけになり、Phase 2 の「長い原稿（20枚程度）」が検証にならない。
- **欄の位置**：p5〜p11 は見本に文言の欄が無い（見出しだけ、または文字が無い）。空いている白い面に、グリッドと 45 度の線を崩さない位置で当方が置いた（例：目次の項目は 45 度の流れに沿って左へずらす、写真＋本文は右の4〜5列）。先方の本テンプレートが届いたら、欄の位置は先方のものに置き換わる。
- **見本の文言**：英字の小見出し（`txt.eyebrow`）の見本を「Company Issues」などから「Dummy Label」に変えた。見本の文言は「ダミー」と分かる形にしておかないと、AI が同じ語を書いたときに `DUMMY_LEFT` が誤って止まる。
- **捨てたもの**：p8（表紙の別案）は表紙でなく「結び」の役割（`closing`）にした。菱形の写真に見出しが重なるので、見出しは1行・副題は短い2行しか入らず、表紙の情報量に足りないため。
- 明朝の太字（強調語）を測るため、Noto Serif JP Bold（OFL）を `fonts/` に足した。描画用の Docker も作り直した。

## D-019 AI の呼び出し口は2つ（本番は Claude API、検証は `claude -p`）

- **何を**：`src/ai/transport.ts` に、`anthropic`（@anthropic-ai/sdk をストリーミングで呼ぶ。本番）と `claude-cli`（Claude Code の `claude -p` を子プロセスで呼ぶ。検証用）の2つを置き、`--ai` で選ぶ。段（A・B）はどちらでも同じコードが動く。
- **なぜ**：この案件用の Anthropic API の鍵がまだ無い。この PC にある他案件の鍵は、費用の付け先と用途が違うので使わない。鍵が届くまでの間も、段の作り・検査・再開を **実物の AI** で確かめるため。
- **`claude -p` で守っていること**：作業場所をリポジトリの外にし、`--system-prompt` で Claude Code の指示を置き換え、道具（`--tools ""`）・設定・MCP・会話の保存を切る。出力の上限は `CLAUDE_CODE_MAX_OUTPUT_TOKENS` で渡す。キャッシュの指定（cache_control）はできないので、9-6 の確認は SDK の経路でしかできない。
- **残ること**：鍵が届いたら、`--ai anthropic` で3本の原稿を通し直し、使用量（キャッシュの読み出しが2回目以降に出るか）と実費を確かめる。

## D-020 AI 呼び出しの決まり（AirLog からの移植と、足したもの）

- 移植：`time-budget.ts`（そのまま）・`models.ts`（形だけ。モデルと単価は 2026-10 の現行に差し替え）・`model-failover.ts`（ストリーミング・廃止時の同格切り替え。原価の DB 記録は外し、記録先を渡す形に）・`doc-policy.ts` の `trimTo`/`redactDevTools`・`brief.ts` の囲いタグを潰す処理。各ファイルの先頭に元のパスと基準コミットを書いた。
- `callForJson`（`src/ai/call-json.ts`）：予算に収まる出力量まで削る／上限を常に伝える／上限で切れた出力は保存せずやり直す（終端にしない）／zod で検証し、形が違えば理由を添えて作り直させる／中身の決まり（数字・件数など）に反すれば、その理由で作り直させる／呼び出しごとに使用量を `ai-calls.jsonl` に追記する。
- 既定のモデルは 9-9 どおり `claude-sonnet-5-5`。effort は `medium`（JSON を書く仕事で、思考に出力の上限を食わせないため）。設定 `ai` で変えられる。
- 安全の判定で断られたとき（stop_reason が refusal）に、サーバー側で別のモデルにやり直させる指定（`fallbacks: "default"`）を既定で入れた（`ai.refusalFallback`）。資料の原稿で断られることはまず無いが、断られたまま空の出力を受け取らないため。
- モデルの出力速度（tok/s）は未実測。AirLog の本番で Sonnet 4.6 が 54.8 tok/s だったので、Sonnet 5.5 は 45 を仮置きした（下限として安全側）。鍵が届いたら実測で埋める。

## D-021 B段の進め方（下書き → 測る → 直す → 型を替える → 丸める）

- 下書きは6ページずつ書かせる（`PLAN_CHUNK_PAGES`）。20枚を1回で書かせると出力が長くなり、上限で切れたときに全部を捨てることになるため。直前のページの型を渡し、同じ型の連続を数える。
- ページごとに、文節の改行を入れ、実フォントで測り、11章の検査（`check/slots.ts`。出来上がった PPTX の検査と同じ関数）を通す。止める指摘があるページだけ、理由（「この欄は最大N字×M行。いまはX字でY行」など）を添えて書き直させる（最大 `ai.maxRewrites` = 2回）。
- それでも欄に入らなければ、同じ役割の別の型で書き直させる（1回）。最後の手段は `trimTo`（語の途中で切らない丸め）で、`TRIMMED` としてレポートに残す。
- 強調が上限を超えたまま残ったときは、超えた分の印を外す（強調の量はコードで保証する）。
- 途中の結果（下書き・ページごと）は `out/<実行ID>/plan/` に書き、落ちても続きから再開する。済んだ段の AI は呼び直さない。

## D-022 検査の細かい決め

- **数字**：桁区切り・全角を外して同じ数として比べる（「２，０００」＝「2,000」＝「2000」）。漢数字（「三つ」「数百万」）は調べない（「一元管理」などの語と区別できないため）。
- **数字の表記**：AI が「4,800」を「4800」と書いたら、原稿の表記（桁区切り）に戻す。値は変えない。
- **単位の欄に数字を入れない**（新しいコード `SLOT_RULE`）：「件→6件」のように単位の欄に変化を詰め込む書き方が出たため。B段では書き直させ、残れば注意。対象の欄は設定 `checks.noNumberSlots`（既定 `txt.unit.*`）。
- **固有名詞らしき語**（`NAME_NOT_IN_SOURCE`、注意）：英字の語・3字以上のカタカナ語・会社の表記のうち、原稿に無いもの。一般のカタカナ語（「スマホ」など）も拾うので、レポートで人が見る前提。英字の小見出し（`txt.eyebrow`）は飾りなので調べない（設定 `checks.nameIgnoreSlots`）。
- **ダミー**：見本と同じ文言・「ダミー」「Dummy」を含む・空の欄を `DUMMY_LEFT` にする。
- **出来上がった PPTX を読み直して測る**：設計図ではなくファイルの中身を検査する。強調は下線の付いた run を [[ ]] に戻して、太字の実フォントで測る。

## D-023 文節の改行は「行の長さをそろえる」

- 見出しなどは budoux の文節で改行する（7章B-4）。文節を前から詰めるだけだと「アプリで打刻、集計は／自動」のように最後の行だけ極端に短くなるので、同じ行数のうち「いちばん長い行」が最も短くなる切り方を選ぶ。
- 文節で切ると欄に入らず、ふつうの折り返しなら入るときは、ふつうの折り返しに任せる（字を削らせるより、語の途中で折り返すほうを選ぶ）。
- 本文（`txt.body` など）には入れない。後で人が直すとき、固定の改行が邪魔になるため（設定 `phraseBreak`）。
- 強調語（[[ ]]）の内側では切らない。強調語は太字の実フォントで測る（D-009 の太字で幅が広がる分を見逃さない）。

## D-024 折り返せない語の幅も測る（実物で見つけた見逃し）

- 20枚の原稿で、数値の欄に「4,800」が入り、描画では「4,80／0」と2行に割れたのに、検査は通っていた。
- 原因：折り返しの予測は「折り返せないひとかたまり（数字・英単語）」を行の先頭に置くと、枠より広くても1行と数えていた。実物の描画（LibreOffice・PowerPoint）はそこで無理に折り返す。
- 直し：`fitSlot` で、折り返したあとの行ごとの幅も測り、枠より広い行があれば `OVERFLOW`（「『4,800』が1行に入らない」）。行末にぶら下げる句読点は数えない。
- 直したあと、同じページを B段からやり直すと、AI は2回の書き直しで「4,800」を幅の広い真ん中の列へ移し、止める指摘は 0 になった。

# Phase 3：写真

## D-025 写真の段（C段）の作り

- **割り当て（AI 1回）**：B段が欄ごとに書いた「どんな写真が合うか」と、支給の写真の説明（`photos.json`）を突き合わせ、欄ごとに「支給の写真」か「生成（場面の説明）」を決めさせる。資料全体の登場人物・服装・場所（cast）もここで決める。決まり（同じページで同じ写真を使わない・1枚を使う回数 `photos.maxUsesPerFile`・生成の枚数 `photos.maxGenerate`・初めて使う生成写真には場面）はコードで確かめ、反していれば理由を添えて作り直させる。
- **生成**：gpt-image-2.5-flare（`photos.model`・`photos.quality`）。1枚ずつ作り、作ったらすぐ保存する（落ちても払い直さない。再開すると作った分は飛ばす）。2枚目からは、最初に作った写真と直前に作った写真を見本として渡す（10章「人物・服装・現場をそろえる」）。生成サイズは枠の形に近いもの（縦長・正方形・横長）。
- **プロンプトの必須事項**（10章・AirLog の写真の作法）：文字・数字・ロゴ・看板を入れない（画面・紙・壁・機械・服も）／人物は日本人で業務を実際にしている／自然光・背景を消さない／cast を毎回入れる。
- **加工**：枠の縦横比に切り抜く。切る位置は sharp の attention（人の顔や肌など目立つところを残す。中央で切ると顔が切れることがあった）→ モノクロ → 乗算。

- **人の確認**：生成した写真を加工前の色のまま並べた一覧（`photos/generated-sheet.jpg`）を出す。文字が入っていないかは人が見る（15章）。
- **実費**：生成の使用量（トークン）から単価で計算し、`report.json` の `photos.generationCostUsd` と、文章と合わせた `totalCostUsdEstimate` に出す。

## D-026 見本の写真を渡すと構図まで似る

# Phase 4：検査・描画・作り直し

## D-027 E段の作り

- **描画**（`src/render/render.ts`）：Docker の中で1回で、LibreOffice → PDF、`pdftoppm` → ページの PNG（96dpi＝1280×720）、`pdffonts` → PDF に入ったフォントの一覧を作り、tar にして標準出力で受け取る（D-011）。10枚で約15〜45秒。
- **代わりの字体の検出**：PDF に DejaVu（イメージに入っている代わりの字体）が入っていたら止める。テンプレートの字体が fonts/ に無いまま描かれると、字幅の予測も見た目も別物になるため。
- **見た目の採点**（`src/review/visual.ts`）：ページの画像を5枚ずつ AI に見せ、先方ルールのうち「AI が文言で直せるもの」（はみ出し・語の途中の改行・強調の付け方・繰り返し・詰め込みすぎ）と「人に知らせる写真の問題」（文字が写っている・顔が切れている・内容と合わない）を指摘させる。色・図形・位置・字の大きさはテンプレートが決めるので評価させない。
- **作り直し**：文言の指摘があるページだけを、B段と同じ直し方（`fixPage`。見た目の指摘を最初の書き直しに渡し、その後は測定の検査で収まるまで）で作り直し、組み立て直して描き直し、**作り直したページだけ** を採点し直す。1ページ最大2回（`review.maxRounds`）。直らなかった指摘は `VISUAL_REVIEW`（注意）でレポートに残す。
- **作り直していないページは変えない**：作り直しの前後で、スライドごとの中身（スライドの XML と、そこから参照する画像の中身）の指紋を比べ、`review/changes-N.json` に残す。実物の3本の全ラウンドで、作り直したページ以外の変化は 0。
- **作り直しで決まりを壊さない**：作り直した版が止める検査に反する（例：AI が「半日」を「0.5」と書いた＝原稿に無い数字）か丸めが要るなら、その版は採らず元の版を残す（`revertedByReview`）。
- `report.json` に段ごとの時間（`timingsMs`）・合計（`totalMs`）・AI の使用量と実費・写真の実費・合計の実費を出す。`slidegen check` は AI も描画も呼ばず、保存した描画と採点の結果を読み直す。

## D-028 単位の欄は「単位だけ」

## D-029 明暗の比（LIGHT_DARK_RATIO）の仮の定義

- 「黒」の定義は先方の回答待ち（16章 #4）。明るさ（0〜1）が `lightDarkRatio.darkBelow`（既定 0.5）未満の画素を黒、それ以外を白と数え、白÷黒 が `target ± tolerance` から外れたら注意。既定は無効のまま。

## 先方のデザイナーに相談したいこと（Phase 4 で分かったこと）

## D-043（2026-10-29）英語の資料と、インドの人物の写真

- **きっかけ**：先方から「プロンプトは英語でも問題ないか」「インドでも営業したい。インドの仲間にも英語でいけるなら感触を聞きたい」。それまでは、原稿が英語でも日本語の資料になり（B段の決まり「資料として自然な日本語にする」）、写真の人物は日本人に固定、画面も日本語だけだった。
- **決めたこと**：作るときに **資料の言語**（日本語／英語）と **写真の人物**（日本人／インド人／さまざまな国籍）を選ぶ。`src/plan/locale.ts` に置き、run.json と deck-plan.json（`language`）に残す。記録の無い古い実行は日本語・日本人＝これまでと1文字も変わらない（試験で確認）。
  - 英語を選ぶと、原稿が日本語でも英語に訳して作る（日本の会社がインド向けの提案書を作る使い方）。
- **AI への指示**：指示文は日本語のまま、「文言はすべて英語で書く」決まりを差し込む。欄の上限は英字の数（`maxCharsLatin`）で伝える（全角の字数だと英文には短すぎる）。収まるかの判定は、これまでどおり実フォントで測る（英語の字体は Barlow）。
- **数字**：英語の資料でも「原稿に無い数字は書かない」は同じ。「300万円」を「3 million」と書くと原稿に無い「3」になるので、桁を数字で書かせる（3,000,000 yen）。原稿の「◯千・◯万・◯億」は、桁を数字にした値も原稿どおりと数える。
- **改行**：英語は単語の切れ目で折り返す。日本語の文節の改行（budoux）は入れない。最後の手段の丸めも単語の途中で切らない（`trimWords`）。
- **原稿に無い語の注意**：英語の資料では、普通の英単語（訳した語）を拾わない。略語・語の途中に大文字・英字と数字の混じり（ABC・TaskMate・ISO9001）だけを拾う。
- **見た目の採点**：英語の資料は英語として読み、指摘も英語で書く（使う人が英語で読むため）。英語の「face」も写真の作り直しに回す。
- **写真**：生成の指示の「人物は日本人」を、選んだ人物にする（インド人＝インドの職場での自然な服装）。
- **PowerPoint**：英語の資料は、文字の言語（lang）を en-US にする。日本語のままだと PowerPoint の校正がすべて誤りとして出る。
- **画面**：画面の英語の表示は別のコミット（`X-UI-Lang`）。

## D-044（2026-10-29）表紙を内容で選ぶ：要点3つ・見出しだけ・コラージュ

- **きっかけ**：先方（デザイン側）「表紙のトピックス的な3項目の扱いが対応しきれない部分がありそう。レイアウトのパターンを他に用意するといいのかも」。
- **原因**：表紙の型が「写真＋要点3つ」の1つしか無く、どの原稿でも表紙に要点を3つ並べていた。原稿に柱となる要点が3つ無いと、AI が箱を埋めるために原稿を言い換えて3つ作る（短く薄い要点になり、箱の下半分が空く）。先方 PDF の 8 ページ目（表紙の別案＝コラージュ）も、表紙としては使っていなかった。
- **決めたこと**：
  - 表紙を3通りにする。①写真＋要点3つ（これまでの `cover`）②**写真＋見出しだけ**（`cover/plain`・新しく足した。要点の箱が無い分、写真を右端まで広げ、左上の白い三角・見出しの黒い帯・副題の白い面・右下の三角は①と同じ位置）③写真コラージュ（`collage`。役割に cover を足した）。
  - ページ割り（A段）：表紙の details（要点）は、原稿が資料全体の柱としてはっきり並べている要点がちょうど3つあるときだけ入れる。無ければ空。
  - 型の選択（B段）：要点の箱の数より原稿の要点が少ない表紙を選んだら、コードが止めて箱の無い表紙を選び直させる（`draftProblems`）。
  - 仕上げの画面の「形を替える」で、3通りから人が選び直せる（同じ役割の型として出る）。
- 足した型はテンプレートの最後（16枚目）に置いた。既存の型のスライド番号は変えていない（試験と、作った資料の型の位置を保つ）。
- これより前に作った資料は、その資料のテンプレートの写しを使うので、新しい表紙は出ない（新しく作る資料から使える）。
