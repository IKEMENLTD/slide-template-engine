## Phase 0 の前提（着手前に返すことになっていた3点）

要件定義書 0章の手順では、全文を読んだあと、下の3点を返して承認を待つことになっている。2026-10-26 に佐藤さんから「進めて」と指示があったので、承認を待たずに Phase 0 を実施した。3点はここに残す。

### 理解した要点

1. 原稿 → 設計図（deck-plan.json）→ .pptx／PDF を作る CLI を作る。AI の出力は設計図で止まり、その先はコードだけで進む。
2. デザインの正本はデザイナーが作る PowerPoint テンプレート。見本スライドを複製し、名前の付いた図形（txt./num./img.）の中身だけを差し替える。
3. AI が決めるのは、型・欄ごとの文言・強調する語だけ。色・位置・大きさ・フォントは決めさせない。
4. 字は小さくしない。入らなければ削るか、別の型を使う。原稿に無い数字・固有名詞は検査で止める。
5. 字数の上限・型の情報はカタログに1か所だけ置き、プロンプトと検査の両方がそこから読む。
6. Phase 0 では、pptx-automizer・LibreOffice での描画・gpt-image-2.5-flare・fontkit の4点を実物で確かめる。

### Phase 0 の作業計画（実施済み）

1. 検証用の小さいテンプレート（名前付き図形・平行四辺形の写真枠・テーマ色）をスクリプトで作る
2. pptx-automizer で複製・差し替えを行い、出力の構造を機械で検査する
3. LibreOffice（Docker）で PDF と PNG にして見た目を確かめる
4. gpt-image-2.5-flare で、生成 → 見本1枚の編集 → 見本2枚の編集 を行う
5. fontkit の予測と LibreOffice の折り返しを 36 通りで突き合わせる
6. PowerPoint で開く確認は人（佐藤さん）が行う → `out/phase0/README.md`

## D-002 スライドの大きさは PowerPoint 標準のワイド（13.333 × 7.5 in）

- 先方 PDF は 1920 × 1080 pt。PowerPoint の標準ワイド（960 × 540 pt）にちょうど 0.5 倍で写る。
- 1920 pt の幅のまま作ると、PowerPoint の既定の文字の大きさや画面表示と合わず、先方が直すときに扱いにくい。
- 仮テンプレートの座標は「PDF の pt × 0.5」で書く。

## D-003 写真の切り抜きは sharp で先に行う

- **何を**：枠の縦横比に合わせた切り抜きとモノクロ化を sharp で済ませてから、automizer の `setRelationTarget` で画像だけ差し替える。
- **なぜ**：automizer 0.9.4 の `setRelationTargetCover`（縦横比に合わせて切り抜く機能）は、平行四辺形の写真で `Skipped setting relation target cropped due to an error: Cannot read properties of undefined (reading 'getAttribute')` を出して切り抜きを飛ばした（画像は差し替わるが引き伸ばされる）。要件 7章 C にもともと「sharp で切り抜く」とあるので、その通りにする。
- **分かったこと**：中央で切り抜くと、人物の顔が平行四辺形の斜めの辺で切れることがある（`render/probe-out-01.png`）。Phase 3 で、写真ごとの「切り抜きの中心」（`photos.json` で指定、無ければ sharp の `attention`）を入れる。

## D-004 automizer の出力は「掃除」と「構造検査」を必ず通す

- **何を**：`src/assemble/sanitize.ts`（掃除）と `src/check/pptx-structure.ts`（PPTX_REPAIR の構造検査）を作った。
- **なぜ**：automizer の出力をそのまま調べると、構造の問題が **8件** あった（`evidence.json` の `raw.issues`）。
  - `removeExistingSlides` で外した見本スライドとそのノートが、部品として残る。`cleanup: false` だと、スライドとノートが互いに参照し合う輪になって残る。「どこからも参照されていない」という数え方では見つからず、**ルートからたどれるか**で数える必要があった
  - 写真を差し替えると、元の画像への関係が残る。`cleanup: true` では画像だけが消え、関係が宙に浮く（PowerPoint が「修復」を出す典型）
  - 見本スライドのノート（型の YAML）が成果物に写る
- **掃除の中身**：スライドからノートへの関係を外す／本文で使われていない画像の関係を外す／ルートからたどれない部品を、変化が無くなるまで消す。足すことはしない。掃除後は **0件**。
- **テスト**：正しいものは通る・壊したものは落ちる、の両側（`test/pptx-structure.test.ts`）。検査と掃除をわざと壊すと、テストが落ちることも確かめた。
- **捨てたもの**：automizer の `cleanup` に任せること。
- **残る不確かさ**：この検査は「PowerPoint が修復を出す原因の典型」を数えるだけで、通っても PowerPoint で開ける保証にはならない。最終確認は人が PowerPoint で行う。

## D-005 フォントは静的フォント（.otf）を使い、太さごとに名前で指定する

- **何を**：`fonts/` に Noto Sans JP（Regular・Medium・Bold）、Noto Serif JP（Regular・Medium）、Barlow（Regular・Medium）の**静的フォント**を置く。可変フォントは置かない。
- **なぜ**：
  - Windows に標準で入っている `NotoSansJP-VF.ttf` は可変フォントで、既定の太さが **Thin**。Windows の LibreOffice で描くと、PDF に `NotoSansJP-Thin` が埋め込まれた（細い字で描かれる）
  - PowerPoint の文字の書式は「太字かどうか」しか持たない。Medium は別の名前で指定する必要がある。静的フォントの Medium は名前表の旧来の家族名が **`Noto Sans JP Medium`** なので、テンプレートではこの名前で指定する（fontkit で名前表を読んで確認）
  - DIN の代わりの Barlow は Windows に入っていない
- **描画**：Docker のイメージには、OS の日本語フォントを入れず、`fonts/` だけを入れた。テンプレートが指定したフォントが無いと DejaVu で描かれるので、すぐに気づける。
- **未確認**：PowerPoint が `Noto Sans JP Medium` という名前で Medium を選ぶか（人が確認する）。.otf は PowerPoint にフォントとして埋め込めない（要件の付録A）ので、先方の PC にフォントを入れてもらう必要がある。

## D-006 文字幅の予測の規則と、3% の余裕

- **規則**（`src/fit/measure.ts`）：和文は文字の間ならどこでも折り返せる／行頭禁則（句読点・閉じ括弧・小書きの仮名・長音）／行末禁則（開き括弧）／英数字の連続は途中で折り返さない／和文と英数字の境目の空き（autospace）／句読点のぶら下げ。
- **突き合わせ**（4 字体 × 3 サイズ × 3 幅＝36 件、LibreOffice 7.4）：

| 設定 | 行数が一致 | 改行位置まで一致 | 実物のほうが行が多い（あふれを見逃す） |
|---|---|---|---|
| 何もしない | 32/36 | 15/36 | 1 |
| autospace 0.25em・ぶら下げあり | 34/36 | 27/36 | 2 |
| 上＋LibreOffice の丸めを再現 | 35/36 | 32/36 | 0 |
| **autospace 0.25em・ぶら下げあり・幅の 3% を余裕** | 31/36 | 10/36 | **0** |

- **分かったこと**：
  - LibreOffice は 1 文字の幅を 1/100mm に丸めて足す（20pt の全角は 20.01pt）。そのため、枠の幅がちょうど 20pt の倍数だと 1 文字少なく折り返す
  - 和文と英数字の間に、およそ 0.25em の空きが自動で入る（PDF の文字の位置で実測）
  - 句読点は枠の外にぶら下げる
  - 読点を含む行が、計算より 1 文字多く入る場合が 4 件残った（原因は特定できていない。どれも予測のほうが行が多い、安全な側のずれ）
- **決めたこと**：B段・検査（OVERFLOW）での判定は「autospace 0.25em・ぶら下げあり・幅の 3% を余裕」にする。改行位置までは合わせない（PowerPoint と LibreOffice で違うので、片方に合わせる意味が薄い）。目的は「予測では入るのに、実物ではあふれる」を 0 にすること。値は設定ファイルに置く。
- **捨てたもの**：LibreOffice の丸めを本番の判定で再現すること（描画側の都合に寄せすぎる。検証の再現用にだけ残した）。
- **PowerPoint での突き合わせ（2026-10-26）**：佐藤さんに PowerPoint for the web で `wrap.pptx` を PDF に書き出してもらった（`out/phase0/wrap/powerpoint.pdf`。14ページ・960×540pt）。
  - **ブラウザ版は Noto を持たず、和文を MS ゴシック・英数字を Calibri に置き換えて描いた**（PDF の埋め込み字体で確認）。そのため Noto の文字幅は確かめられない。代わりに、置き換わった字体の幅で予測し直し、**PowerPoint の折り返しの規則**を確かめた（`scripts/phase0/measure-wrap-substituted.ts`。MS ゴシックと Calibri は Windows 同梱の有償フォントなのでリポジトリに入れない）。
  - **PowerPoint は和文と英数字の間に空きを入れない**（実測 ±0.03em）。LibreOffice（0.25em）と違う。
  - 句読点はぶら下げる（LibreOffice と同じ）。
  - 太字の字体が無いとき（MS ゴシック）は、PowerPoint が太字を合成し、1文字の幅が約 0.75% 広がる（20pt で 20.15pt）。

| 設定（PowerPoint・置き換わった字体の幅で予測） | 行数が一致 | 改行位置まで一致 | 見逃し |
|---|---|---|---|
| 空きなし・ぶら下げあり | **36/36** | 31/36 | 0 |
| 空き 0.25em・ぶら下げあり・3% の余裕（本番の判定） | 28/36 | 6/36 | **0** |

- **結論**：本番の判定（空き 0.25em・ぶら下げ・3% の余裕）は、LibreOffice でも PowerPoint でも「あふれの見逃し 0 件」。PowerPoint より空きを多めに見積もるぶん安全側に倒れる。改行位置を PowerPoint に合わせたいときは、空きを 0 にした設定を使えばよい（値は設定ファイルに置く）。
- **まだ確かめられていないこと**：Noto が入った PowerPoint（デスクトップ版）での文字幅。規則は確かめたので、残るのは字体の幅の差だけ。3% の余裕でまかなえる見込みだが、PowerPoint のデスクトップ版が使えるようになったら同じ道具で測り直す。

## D-008 先方資料の読み直し（要件定義書 4章の訂正）

- **大見出しは明朝**：PDF の大見出しはリュウミン（明朝）で、ルール文書と一致している。16章 #3 の既定値「明朝を使わない」は、資料に合わせて **`headline.mincho: true`（代わりの字体は Noto Serif JP）** にするのがよい。Phase 1 の設定の雛形はこの値で作る。先方に確認したいのは「リュウミンの代わりに Noto Serif JP でよいか」の 1 点になる。
- **ゴシックは太ゴB101も使っている**：小見出し・説明文の一部が太ゴB101（モリサワ・有償）。代わりは Noto Sans JP Bold にする。
- **4ページ目は型ではない**：説明のページ。16章 #7 は「型として扱わない」で確定。
- **8ページ目は表紙の別案**：役割は `cover`。

## D-009 強調は「太字＋アクセント色の下線」

- **何を**：強調語は、見本の書式に太字と accent2 色の太い下線を足す。設定は `emphasis: { underline: "accent2", bold: true }` の形にする（6-3 の `color: accent2` から変える）。
- **なぜ**：黄の文字色は白地で読めない。ルール文書 4-4 が挙げる強調の形（黄の下線・黄の図形の中の文字）に合わせる。
- **残ること**：「黄色の図形の中の文字」で強調する型は、図形をテンプレートの飾りとして作り込む（エンジンは図形を足さない）。

## D-010 「グリッドの幅を広げる」は型の選び直しで行う

- ルール文書 8-4 の「必要であれば使用するグリッドの幅を広げる」は、エンジンが枠を広げることではなく、**欄の広い型を選び直す**ことで行う。要件定義書の原則4（枠を広げない）と両立する。
- そのため、件数違いと同じく、文字の多い欄には「幅の広い変種」をテンプレートに用意してもらう必要がある（Phase 5 の手順書に書く）。

## D-011 描画は Docker（標準入出力で受け渡す）

- `docker/render/Dockerfile`：debian bookworm-slim・LibreOffice 7.4.7・poppler-utils・`fonts/`。
- 検証機の docker コマンドは Windows 側のもので、WSL のパスを bind できないため、PPTX を標準入力で渡し PDF を標準出力で受け取る（`scripts/phase0/render.py`）。
- Phase 0 では PNG 化に PyMuPDF を使った（検証機に pdftoppm が無いため）。Phase 4 では Docker の中の pdftoppm を使う。
- Windows の LibreOffice（soffice.exe）でも描けたが、WSL との連携が途中で止まる（`UtilAcceptVsock: accept4 failed`）ことがあり、フォントも可変フォントを拾うので使わない。
